The short answerYou were right, and it has one cause

Fifty people were each given one real job. None of them finished cleanly. Twenty-four got something out of the app but would have to redo part of it by hand; sixteen were offered a feature that then failed or saved nothing; ten found no path at all. Twenty-four of the fifty are blockers — the job cannot be done, or the factory receives something wrong.

The important part is that this is not fifty separate faults. Four of the five things you said were broken trace back to one line repeated in three files, and most of the rest fall into three repeating habits: records created without the thing they exist to hold, fields written but never read, and the app stating on screen that it produced something it cannot produce.

Your own words were “I don't think it does what you think it does.” That is the correct reading. The previous round of fixes was real — the hardcoded seam rows are genuinely gone, preflight genuinely blocks, the code splitting genuinely happened — but they were verified by reading the code rather than by using it, and the layer underneath was never exercised.

Root causeEvery reference and every logo is thrown away before the model sees it

One parameter, three files

Every image generator in the app builds a list of your reference images — and, in Make, the logo you picked with its placement and millimetre width — and passes them to the image service like this:

const res = await base44.asServiceRole.integrations.Core.GenerateImage({
  prompt: fullPrompt,
  existing_image_urls: existing.length ? existing : null,   // ← the references and the logo
});

The Base44 SDK on version 0.8.44 declares that endpoint as taking exactly one field:

export interface GenerateImageParams {
    /** Description of the image to generate. */
    prompt: string;
}

The string existing_image_urls appears nowhere in the SDK. The same codebase gets this right elsewhere: breakDownDesign sends its image through the documented file_urls parameter, which is why reading a design works while generating from one does not.

What I can and cannot prove. The SDK forwards whatever object you hand it, so the key does reach Base44's server. I could not test whether the server honours it — the app is behind a login I don't have, and I would not spend your image credits guessing. So: unsupported, unacknowledged, and contradicted by the working call in the next file. One controlled call settles it, and that is why it is the first thing on the fix list.

  • 1
    “The reference thing doesn't work” — all the model is guaranteed to receive is one sentence: “Take colour, material and detailing cues from the supplied reference images.” With, possibly, nothing supplied.
  • 2
    “Make something doesn't allow adding of logos” — the picker is wired and does send the mark. But the mark rides the same key, and the placement and mm width you set are React state with no field to save into, so they never reach a Placement record either.
  • 3
    “It needs to think how the logos are used” — the prompt does tell the model to copy the mark exactly and not to redraw it. If the image never arrives, that instruction guarantees the one thing your brand rules forbid: an invented lookalike.
  • 4
    “Port them over to see how they'd look on a garment” — blocked for a second, separate reason: the on-garment panel needs the component to have a picture, and breaking a design down creates components with no image at all.
